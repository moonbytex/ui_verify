DevEco CLI · UI 意图校验 · 基于多模态大模型

写一句话
AI 替你点完整个 App

devecocli verify 把自然语言写的测试计划交给一组多模态 AI 智能体。它们只看截图就能在真机或模拟器上 点击、滑动、输入、旋转、折叠，并逐步判断界面是否符合预期，最后给出结论、成功步骤、失败步骤、日志和截图。 


  

  

    
0 行测试代码，只写自然语言

    
6 个协作智能体，同一进程

    
2 路每轮并行：判状态 + 想动作

    
0 依赖不读控件树，纯视觉定位

    
≤30 轮防死循环上限

  






  
核心特点 WHY IT'S DIFFERENT

  
传统 UI 自动化要写脚本，要按控件 id 找元素，界面一改脚本就坏。verify 把这些都交给模型去看、去想、去判断，开发者只需要描述"做什么、期望看到什么"。

  

    
💬
自然语言即测试用例

      
测试计划就是一段中文（最长 3000 字），写清每一步的操作和预期结果。不需要录制，也不需要写选择器或断言代码。

      --test-plan "点击登录→进入首页→看到商城入口"

    
👁️
纯视觉定位，不依赖控件树

      
模型只看截图，直接给出点击坐标，再由程序换算成物理像素交给 uitest。重构布局、换 id、用 Canvas 或 Web 自绘的界面，都照样能测。

      999×999 归一化坐标 → clamp 到屏幕像素

    
⚡
判状态与想动作并行

      
每一轮 StatusAgent 判断当前状态，ActionAgent 同时预先想好下一步。状态是 normal 就直接执行，等待时间几乎减半；状态是 abnormal 才丢掉预取的动作重新规划。

      Promise 并行 · 投机执行

    
🧠
多智能体分工

      
计划校验、历史匹配、动作决策、状态判断、回放、总结，由 6 个智能体分别负责。它们共享同一份历史数组，每个智能体再按自己的视角把历史翻译成对话。

      Validation · Matcher · Action · Status · Fake · Summary

    
🔁
自愈与重试

      
点偏了、有弹窗挡着，会判成 abnormal，然后基于最新截图重新定位。同一步最多重试 3 次，总共最多 30 轮。连续判断原地踏步时会提醒模型重新看计划和截图。

      abnormal ×3 → error

    
💾
步骤记忆 + 像素差回放

      
测过的路径会存成 step memory。下次遇到相似的计划时，FakeActionAgent 不调模型，直接重放这些步骤；画面和历史差异超过 1% 时，再交还给模型接管。

      省 token · 提速

    
🎞️
多帧稳定截图

      
后台一直截图。操作之后等画面稳定，最多 3 秒，再挑出有变化的关键帧（最多 6 帧）发给模型，所以 Toast、短暂弹出的弹窗也能捕捉到。

      像素差 · 去状态栏干扰

    
📱
多设备 + 模拟器专属能力

      
支持手机、平板、2in1 和折叠屏。在模拟器上可以快速截取帧缓冲、旋转屏幕、切换折叠态，并自动修正截图方向。

      setRotation · setFoldState

    
🧩
MCP 标准接口，AI 编程闭环

      
引擎本身就是一个 MCP Server，CLI 只是其中一个客户端。Cursor 等 AI 编程工具可以直接调用 verifyUI，走完"写代码 → 构建 → 校验 → 修复"的循环。

      JSON-RPC 2.0 · stdio

MCP 交互 Model Context Protocol

  
verify 的引擎 ui-verification-mcp 是一个标准 stdio MCP Server。CLI 找到依赖包里的 bin/ui-verification-mcp.cjs，用当前 Node 拉起它，再由它启动 dist/uiVerification.mjs，标准输入输出原样转接。之后 CLI 在 stdin/stdout 上一行一条 JSON-RPC 和它交谈。点击下方各步骤查看报文。

  

    

      

        
        
        
        
        
        
      

      

    

    

      

        
工具作用

        
verifyUI完整跑一遍测试，返回 success / reason / successPart / failPart / id

        
getLog按 id 读取本次任务收集的 hilog，数据在进程内存里

        
saveScreenshot按 id 把内存里的截图写到指定目录

      

      
设计要点

      
    
        
  • 密钥不进参数：baseUrl、API Key、模型名、hdc 路径都通过子进程环境变量 UI_VERIFY_* 传递，不出现在 JSON-RPC 报文里。
    • 
        
  • 进度实时可见：每次判完状态，MCP 推送一条 notifications/progress，CLI 把它显示成 spinner 上的 3/5 原因。
    • 
        
  • 超时与取消：一次调用最多等 10 分钟。按 Ctrl+C 时，Windows 上用 taskkill /t /f 结束整棵进程树。
    • 
        
  • 设备任务锁：在设备 /data/local/tmp 写锁文件，每 10 秒刷新一次，防止多个任务同时操作同一台设备。
    • 
        
  • 一个引擎，两种入口：CLI 用户执行 devecocli verify；AI IDE 把它配置成 MCP 后直接调用 verifyUI。
    • 
      

    

  






  
多智能体 6 AGENTS · 1 PROCESS

  
六个智能体都是 MCP 进程里的类，没有各自独立的进程，靠共享同一份历史数组协作。模型每次只能调用一个"出口工具"，所以每个智能体的输出都是结构化、可校验的。

  

    
InputValidationAgent

      
⏱ 任务开始 · 与 Home、匹配并行
⇢ get_input_validation_result

      
结合设备能力清单（设备类型、是否模拟器、是否可折叠、支持哪些操作），判断这份计划能不能在当前设备上执行。不通过就直接失败，返回 [计划校验失败]。

    
InputMatcherAgent

      
⏱ freshStart=true 且有同设备、同包名的记忆
⇢ get_match_result

      
把用户计划和已保存的计划列表对比，选出一份可以重放的历史，没有合适的就不用。

    
FakeActionAgent

      
⏱ 匹配成功时替代第一轮 Action
⇢ 不调用模型

      
按原来的坐标和时间间隔重放动作。新截图与旧截图的像素差超过 1% 就停止回放，转入正常循环。

    
ActionAgent

      
⏱ 每一轮 · 与 Status 并行
⇢ tap / swipe / inputText / startApp / setRotation …

      
根据计划、历史截图和以往动作给出下一步，也可以选择本轮不操作。硬约束：touchDown 之后必须紧跟 touchUp。

    
StatusAgent

      
⏱ 每一轮 · 与 Action 并行
⇢ returnStatus

      
对比计划和截图，判断为 normal / abnormal / completed / error，并给出 progress/total 和原因。在模拟器上必须按物理方向判断横竖屏。

    
SummaryAgent

      
⏱ completed 或 error 之后
⇢ get_summary_result

      
阅读全部历史，写出 successPart 和 failPart，形成人能看懂的测试报告。

为什么 Qwen2.5 要特殊处理？

  
启动时按模型名匹配 /qwen2\.5/i，选择两套不同的定位器（imageLocator）和对话方式（chat）。根本原因是：不同模型训练时学到的"坐标语言"不一样。

  

    
📐
通用模型：相对坐标
Qwen3-VL 等模型惯用归一化坐标（0~999 或 0~1000），与图片实际像素无关。所以送多大的图都可以，系统提示里写明"屏幕是 999×999"，回来的点按比例换算就行。
坐标 ÷ 999 × 屏幕宽高

    
🎯
Qwen2.5-VL：绝对像素坐标
Qwen2.5-VL 训练时用的是输入图片上的绝对像素坐标，例如 [322, 715] 就表示它所看到的那张图上的第 322 列、第 715 行。如果告诉它"999×999"，反而和它的习惯冲突，点击位置会偏。所以不加任何坐标提示，直接把它输出的数当作位图像素。
坐标 ÷ 位图宽高 × 屏幕宽高

    
🧱
为什么要对齐到 28 的倍数
Qwen2.5-VL 的视觉编码器以 14px 为一个 patch，再把 2×2 个 patch 合并，所以图像边长要是 28 的倍数；不是的话，服务端会自己再缩放一次（smart_resize）。这样一来，模型看到的图和本地以为的位图尺寸就对不上，坐标就会算错。本地预先缩放到 28 的倍数，并限制在 480~1424 之间，服务端就不会再改动，模型坐标和本地位图一一对应。（这里的"服务端二次缩放"是按 Qwen2.5-VL 的公开机制推断的设计意图；源码中能看到的是 28、480、1424 这三个常量和对应的缩放逻辑）

// 源码中的两个定位器（简化）
class GenericLocator {                 // 非 qwen2.5
  getPrompt()   { return "屏幕宽高为999x999，坐标原点在左上角"; }
  getSuitableImageSize([W,H]) { return [floor(W*2/3), floor(H*2/3)]; }
  pointInterp([x,y], _img, [W,H]) {
    return [clamp(round(x*W/999),1,W), clamp(round(y*H/999),1,H)];
  }
}
class Qwen25Locator {
  getPrompt()   { return ""; }           // 不给坐标约定
  getSuitableImageSize([W,H]) {
    let w = round(W/28)*28, h = round(H/28)*28;
    if (max(w,h) > 1424) { s = max(w,h)/1424; w = floor(w/s/28)*28; h = floor(h/s/28)*28; }
    if (min(w,h) <  480) { s = 480/min(w,h);  w = ceil(w*s/28)*28;  h = ceil(h*s/28)*28;  }
    return [w, h];
  }
  pointInterp([x,y], [Iw,Ih], [W,H]) {   // Iw,Ih = 历史里最后一张图解码后的宽高
    return [clamp(round(x*W/Iw),1,W), clamp(round(y*H/Ih),1,H)];
  }
}

  

  

    
差异点通用模型Qwen2.5（额外的兼容处理）

    
工具调用OpenAI 标准 tools 字段，模型返回 tool_calls很多 Qwen2.5-VL 部署对 tools 字段支持不稳定 → 把工具说明写进 system 文本，要求模型输出 {"tool_calls":[...]} JSON，再从回复文本中提取最后一个 JSON 解析出来

    
非法工具名JSON Schema 校验模型编造 terminate/finish 等工具时，追加"[工具调用错误] 可用工具为…"后重试

    
启动应用按提示词执行第一步如果是 swipe（想在桌面上找图标），注入提示"请调用 startApp"后重试

    
原地打转没有这项额外检测另外检测同一个操作连续 5 次，注入"界面可能未变化，请重新分析"

    
空回复—模型返回空 message 时，按 2s、4s… 递增等待后重试

  


  
截图流水线：后台持续采集 + 稳定帧挑选

  

    
📸
后台截图循环
真机连续执行 snapshot_display -w -h，在设备端缩放。模拟器（Emulator ≥ 26）用 -screenshot 直接取帧缓冲 PNG，按方向差旋转校正后转成 JPEG（质量 80）。

    
🧹
动作前清缓存
执行点击前先清空思考期间堆积的帧，保证模型下一轮看到的一定是动作之后的画面。

    
⏳
3 秒稳定判定
不断取帧，直到最近 800ms 内相邻帧像素差都小于 1%，或者满 3 秒。像素差计算时裁掉状态栏，避免时钟跳动被当成界面变化。

    
🎯
关键帧挑选
去掉开头没有变化的帧，按 500ms 间隔抽样，再去掉静止的重复帧。超过 6 帧时保留前 3 帧、最后 1 帧和中间变化最大的 2 帧，所以 Toast 也能被看到。

  






  
共享历史数组 智能体之间的"黑板"

  
一次 verifyUI 只有一份按时间追加的历史数组，所有智能体读的都是它。它不是对话记录，每个智能体发请求前才把它翻译成自己的消息。正常推进时，数组尾部按下面的顺序增长：

  

  

    
image
base64List：按时间排列的多帧图像
screenSize：最后一帧对应的物理屏幕宽高

    
status
status / reason / progress / total
abnormalRetryCount：当前步骤的异常重试计数

    
action
name：tap / swipe / inputText / startApp / setFoldState …
point：保存的是模型坐标，不是物理像素

    
log
这段时间的 hilog 原文，写入 log.md 并供 getLog 读取。不发给任何智能体，hilog 不参与对错判断。

  






  
三类信号 + 步骤记忆 结果怎么来

  

    
信号来源用来判断不用来判断

    
👁️ 模型看图StatusAgent界面是否符合计划预期：点错、弹窗挡路、目标不存在不读 hilog / faultlog

    
🧮 像素变化动作后的等待 · FakeActionAgent画面有没有变化，回放能否继续不区分"点偏了"和"卡住了"

    
💥 新增 faultlog任务结束时 checkErrorappfreeze / cppcrash / jscrash 等，拉取到本机后把路径拼进 reason不改变 success 的取值

  

  

    
💾
何时保存记忆
状态为 error、中途没有出现 abnormal、freshStart=true，并且第一个动作是 startApp 时，把到最后一个 normal 为止的步骤保存到 stepMemory/（版本 1.0.2）。

    
▶️
何时重放
下一次同设备、同包名且 freshStart=true 时，由 InputMatcherAgent 选出匹配的记忆，FakeActionAgent 按原坐标和原时间间隔重放。

    
🛑
何时停止重放
每一步都拿新截图和旧截图做像素差，超过 0.01 就说明界面已经不同，立即交还给 ActionAgent，由模型继续接管。

Q6：ActionAgent 做动作前，能看到 StatusAgent 的结论吗？

  
要看是哪一轮、哪个分支：normal 分支中看不到本轮的结论（因为是并行的），但能看到之前所有轮的结论；abnormal 分支中会重新请求一次，这时能看到本轮的 abnormal 结论。

  

    
时刻历史数组末尾ActionAgent 请求时能看到什么

    
开局（第 0 次动作）[img0]只有首图，没有任何 status。由 actionAgent.action() 单独请求，不与 Status 并行，通常第一步是 startApp

    
第 1 轮 · normal[img0, log, act0, img1]img1 + 之前的动作。本轮 status₁ 还在计算中，看不到，与 StatusAgent 同时发出请求

    
　→ 写入… img1, status₁, log, act1先写 status₁ 再写 act1，所以数组顺序看起来像"先判状态后动作"

    
第 2 轮 · normal… act1, img2能看到 status₁（上一轮的）和 img2；看不到 status₂

    
第 3 轮 · abnormal… img3, status₃(abnormal)预取的 act 作废，重新调用一次 actionAgent.action()，此时能看到 status₃ 的异常原因，据此重新规划

  

  

    
// 主循环源码（简化）
for (;;) {
  if (last(history).type !== "image") history.push(stableImages());

  const statusP = statusAgent.analyze(plan, history);   // 并行发出
  const actionP = actionAgent.getNextAction(plan, history); // 并行发出
  const status  = await statusP;
  const action  = await actionP;          // 两者看到的是同一份 history

  switch (status.status) {
    case "normal":
      history.push(status, log);
      await actionAgent.executeAction(action);   // 直接用预取的
      break;
    case "abnormal":
      history.push(status);                      // 先写入异常结论
      await actionAgent.action(plan, history);   // 丢掉预取的，重新请求(能看到 abnormal)
      break;
    case "completed": case "error": /* 总结并返回 */
  }
}

    

      
为什么 normal 时不需要等 status？
normal 表示"界面符合预期、继续下一步"。这时 ActionAgent 只看截图得出的下一步，和看到 status 之后得出的基本一致，所以可以先发起请求，省掉一次模型往返。

      
为什么 abnormal 时必须重来？
abnormal 表示"出问题了"，例如被弹窗挡住、点偏了。预取的动作没有考虑这个问题，所以要把异常原因写进历史，让 ActionAgent 看到后再规划。

    

  





  
Q7：截图间隔多久？diff 怎么算？screenshot() 为什么能"取帧"又能"清缓存"？

  

    
⏱️
① 没有固定间隔，所以看起来随机
采集循环是 while(running){ 截一张; 放进 cache }，没有 sleep，拍完立刻拍下一张。间隔完全取决于截一张图要多久：

      真机：每张要串行执行 3~4 条 hdc 命令（读屏幕尺寸 → snapshot_display → base64 读回 → rm），受 USB/网络、设备负载、图片大小影响，通常几百毫秒，并且有波动。

      模拟器：Emulator -screenshot，每 50ms 轮询一次 PNG 是否写完，再旋转、缩放、编码。

      失败时：真机直接重试；模拟器等 500ms 再重试。

    
🧮
② diff = 与"前一张"相比变化像素的占比
两帧解码成 RGBA，裁掉顶部状态栏，逐像素比较（内置 pixelmatch 算法：YIQ 色差超过阈值 0.1 记为不同，忽略抗锯齿边缘像素）。
diff = 不同的像素数 / 区域总像素数，范围 0~1。

      "前一张"指 cache 里的上一帧；如果 cache 刚被取空，真机会和被取走的最后一帧比较，模拟器始终和紧邻的上一帧比较。尺寸不同或解码失败时，diff 记为 1。

    
📦
③ screenshot() = "整盒拿走"
它不会去设备上拍照，只是把 cache 整个数组拿走，并换成一个新的空数组。所以"取帧"和"清缓存"是同一件事的两个方面。cache 为空时，每 100ms（模拟器 50ms）查看一次，最多等 5 秒。
"动作前清缓存"就是调用一次它，并把返回值丢掉。

  

  

    
// 真机采集器（源码简化）
class ScreenCapture {
  cache = [];
  lastImageBeforeConsumed = null;

  async startLoop() {
    while (this.isRunning) {
      const img = await harmony.singleScreenshot(); // 耗时不固定
      this.addImageToCache(img);                    // 不 sleep，立刻下一张
    }
  }
  addImageToCache(img) {
    const prev = this.cache.length ? this.cache.at(-1)
                                   : this.lastImageBeforeConsumed;
    img.diff = prev ? pixelDiff(prev, img, {y: statusBarHeight}) : 1;
    this.lastImageBeforeConsumed = null;
    this.cache.push(img);
  }
  screenshot() {                  // 取走 = 清空
    const taken = this.cache;
    this.lastImageBeforeConsumed = taken.at(-1); // 留作下一张的比较基准
    this.cache = [];
    return taken;
  }
  waitUntilChange(ms) {           // 只看不取
    // 等到 cache 中出现"晚于调用时刻且 diff>0.001"的帧，最多 ms 毫秒
  }
}

    
// 时间线示例（真机，数字为实测量级）
t=0.00  拍 A   cache=[A(diff 1)]          ← 首帧无参照
t=0.42  拍 B   cache=[A, B(0.0002)]
t=0.95  拍 C   cache=[A, B, C(0.0001)]    ← 间隔 0.42 / 0.53，不均匀
t=1.00  screenshot() → 返回 [A,B,C]，cache=[]，基准=C
t=1.31  拍 D   cache=[D(与C比 0.0003)]
t=1.70  执行 tap
t=1.88  拍 E   cache=[D, E(0.2870)]       ← 界面开始变化
        waitUntilChange 发现 E 的 diff>0.001 → 返回

pixelDiff(上一帧, 当前帧):
  1. 两图解码成 RGBA，裁掉 y < 状态栏高度 的部分
  2. 逐像素计算 YIQ 色差，大于阈值且不是抗锯齿像素 → 计数+1
  3. return 计数 / (宽 × 高)

阈值：
  waitUntilChange   真机 0.001 / 模拟器 0.01
  稳定判定          0.01，并且持续 ≥ 800ms
  关键帧去重        0.001
  回放比对          0.01

  





  
Q8："最多 3 条带图消息、12 张图" 怎么理解？

  
历史数组在内存中完整保留所有截图。但每次发请求之前，会对翻译好的 messages 做一次"裁剪"：只保留最近几条带图消息中的图片，更早消息里的图片替换成一段文字 "已省略历史截图"，文字内容（状态、动作、原因）全部保留。这样上下文长度和费用不会随轮数无限增长，模型仍然知道过去发生了什么，只是看不到旧图。

  

    

      

        
        
        
      

      

      

    

    
// 源码：每次调用模型前执行 limitImages(messages, 3, 12)
function limitImages(msgs, maxMsgs = 3, maxImgs = 12) {
  const imgMsgIdx = 含有 image_url 的消息下标;
  const total = 这些消息里的图片总数;

  // 两个条件都满足 → 不做处理
  if (total <= maxImgs && imgMsgIdx.length <= maxMsgs) return msgs;

  // 图片总数超过 12 → 只保留最近 2 条；否则保留最近 3 条
  const keep = total > maxImgs ? maxMsgs - 1 : maxMsgs;
  const drop = imgMsgIdx.slice(0, imgMsgIdx.length - keep);

  return msgs.map((m, i) => drop.includes(i)
    ? { ...m, content: m.content.map(p =>
          p.type === "image_url" ? { type:"text", text:"已省略历史截图" } : p) }
    : m);
}

// 只影响本次请求的 messages，不修改内存中的 history
// verify screenshot / saveScreenshot 拿到的仍然是全部截图

  





  
Q1：InputValidationAgent "与 Home、匹配并行" 是什么意思？

  
verifyUI 刚开始、进入主循环之前，有三件互不依赖的准备工作。它们不是一件做完再做下一件，而是同时启动，再用 Promise.all 一起等待。这样总耗时取决于最慢的那件，而不是三件相加。

  

    

      
① 计划校验
InputValidationAgent → 模型 ~2.5s

      
② 计划匹配
InputMatcherAgent → 模型 ~2s

      
③ 按 Home
uitest Home + 等 1.5s

      
Promise.all
三者都完成 → 截首图

      
串行约 2.5 + 2 + 1.5 ≈ 6 秒；并行约 2.5 秒，取决于最慢的那件。

    

    
// ui-verification-mcp 源码（简化）
async verifyUI(testPlan, bundleName, freshStart) {
  const validate = inputValidationAgent.validate(testPlan);   // ①
  const match = freshStart
      ? inputMatcherAgent.match(testPlan, bundleName)          // ②
      : Promise.resolve({ matchedHistory: null });
  const home = (async () => {                                  // ③
    if (freshStart) { await device.pressKey(["Home"]); await sleep(1500); }
  })();

  const [v, m] = await Promise.all([validate, match, home]);
  if (v.status === "inValid") return { success:false, reason:"[计划校验失败]"+v.reason };

  // 以上都通过后，才截第一张图，进入主循环
}

  

  

    
为什么能并行
校验只读计划文本和设备信息；匹配只读本机的 stepMemory 文件；按 Home 只操作设备。三者没有数据依赖。

    
代价
即使计划最后被判为不合格，Home 也已经按下，匹配请求也已经发出。用一点浪费换取速度，计划不合格本来就是少数情况。

    
--no-fresh-start 时
②③ 直接跳过，只做校验，然后在当前画面上开始测试，不回桌面，也不复用记忆。

  





  
Q2：InputMatcherAgent 怎么和之前的计划对比？记忆从哪来？

  
是的，记忆来自之前某一次执行失败的 devecocli verify（或通过 MCP 调用的 verifyUI）。它只在失败时保存：保存的是"走通的那一段前缀"，下次修完 bug 重测时，就能跳过已经验证过的前几步。

  

    
①
第一次运行：失败并存档
计划："1.启动应用 2.点击登录进入首页 3.点击商城→手机 4.点击 Mate 70 看到详情页"
第 4 步判 error（详情页白屏）。同时满足以下条件：
✔ 整个过程没有出现 abnormal
✔ freshStart = true
✔ 第一个动作是 startApp
→ 把历史数组截到最后一个 normal（第 3 步）为止，以 SummaryAgent 写出的 successPart 为 key 保存。

    
②
修复代码后重测：匹配
开发者（或 AI）修好详情页，再次运行同样（或更长）的计划。InputMatcherAgent 读取 同 sessionId + 同设备名 + 同包名 的记忆文件（这几个词的含义见 Q5），把所有 key 作为"已执行计划列表"发给模型，问哪一条可以作为当前计划的完全匹配或前缀匹配。

    
③
重放：FakeActionAgent
模型返回 index=0，取出那份历史，同时从文件中删除这条记忆（一次性使用）。FakeActionAgent 按原坐标重放 startApp → tap 登录 → tap 商城 → tap 手机，每一步都和旧截图做像素差，一致就继续，不一致就停。之后由 ActionAgent 接手第 4 步。

Q3：同一份历史，不同视角，举个例子

  
假设测试已经跑了一轮，内存里的历史数组是左边这样（只有 5 个元素）。每个智能体调用模型前，都把同一个数组翻译成自己的 messages。点右侧的按钮切换视角，看同一个元素变成了什么消息。关键规律：自己产出的内容记为 assistant，别人产出的内容记为 user。

  
⚠️ 注意时间顺序：数组里 [1] status 排在 [3] action 前面，并不代表这个 action 是看完 [1] 才做出的。在 normal 分支里，二者是同一轮并行请求的，只是写入顺序为"先 status、后 action"。这里展示的是下一轮各智能体看到的完整历史。详见 Q6。

  

    

      
history[]（内存中的唯一真相）

      

    

    

      

        
        
        
      

      

      

    

  

  

    
为什么要这样翻译？
Chat 模型最擅长"延续自己的对话"。对 ActionAgent 来说，过去的点击就是它自己调用过的工具（assistant + tool_calls），状态判断是外部给它的反馈。对 StatusAgent 正好反过来：过去的判断是它自己的 returnStatus，点击则是别人告诉它"做了什么"。

    
好处
两个智能体都以为自己在进行一段连贯的多轮工具调用对话，模型的指令遵循和格式稳定性最好。同时只需要维护一份历史，不会出现两份对话记录不一致的问题。

    
log 去哪了？
hilog 也存在历史里（用于 getLog / verify log），但三个视角都会跳过它，所以日志内容不会影响模型对界面的判断。

  





  
Q4：截图流水线举例，"动作前清缓存"是什么意思？

  
后台截图循环一直在拍，拍到的帧都放进一个缓存数组。问题是：模型思考需要 2~5 秒，这段时间里缓存会堆积一堆点击之前的旧画面。如果不清掉，下一轮"取点击后的画面"时会把这些旧帧也一起取走，模型就可能把点击前的画面误当成点击后的结果。
下面以"点击登录按钮"为例，按 ▶ 逐步播放。

  

    
后台截图缓存 cache[]t = 0.0s

    

    

      
      
      
    

    

  

  

    
采集与取用分离
采集循环只管往 cache 末尾追加帧，并计算和上一帧的像素差 diff。screenshot() 一次性取走全部帧并清空 cache。waitUntilChange() 只查看 cache，不取走。

    
清缓存 = 一次"丢弃式"取用
动作执行前调用一次 screenshot()，返回值不写入历史，唯一目的是让 cache 从"点击前最后一张"之后重新开始计数。

    
为什么还要多帧？
点击之后可能先弹出 Toast，1 秒后消失。只取最后一帧就会漏掉。所以最后送给模型的是按时间排列、去重后的几帧，提示词也要求"任一帧出现 Toast 即算出现"。
